# Photobooth

Фотобудка: Canon EDSDK + сублимационный принтер + сенсорный экран.
FastAPI backend + pywebview fullscreen window.

## Структура

```
photobooth/
  python/              ← Python 3.12 embedded + pip + все пакеты
  backend/             ← FastAPI, камера, принтер, облако
  frontend/            ← HTML/CSS/JS интерфейс
  templates/           ← шаблоны печати
  bin/                 ← ffmpeg
  EDSDK_Win/           ← Canon SDK
  app.py               ← точка входа
  requirements.txt
```

`python/` — портативный Python со всеми зависимостями. Заменяет venv.
Создаётся автоматически (см. ниже). В git не хранится.

## Установка

### Вариант А: из релиза (рекомендуется)

```
Скачать photobooth-win.zip из GitHub Releases → распаковать в C:\photobooth\
```

ZIP содержит всё: код, .git, python/ с пакетами. Готово к запуску.

### Вариант Б: из git clone

```
git clone → script_devstart.bat
```

Скрипт сам скачает embedded Python, поставит pip и пакеты.

### Результат одинаковый

Оба варианта дают идентичную структуру. Взаимозаменяемы.

## Запуск

```
Разработка:    script_devstart.bat     (fetch/reset origin/main + pip install + app.py --dev)
Продакшен:     _setup_windows.bat      (киоск-режим, автозапуск при загрузке)
```

## Сборка релиза (GitHub Actions)

При каждом push в main:

```
GitHub Actions (windows-latest)
  → checkout репо
  → скачивает Python 3.12 embedded с python.org
  → pip install -r requirements.txt
  → пакует всё (код + .git + python/) в ZIP
  → публикует как GitHub Release "latest"
```

Постоянная ссылка: `Releases → latest → photobooth-win.zip`

## Обновление

```
Telegram /update
  → VPS скачивает полный Windows release с GitHub
  → VPS перезаписывает artifacts/full.zip
  → VPS последним обновляет status.json
  → администратор отправляет /restart

Запуск app.py
  → читает status.json с Яндекс Диска
  → сравнивает SHA-256 активного ZIP с .update_hash
  → скачивает ZIP и проверяет размер + SHA-256
  → распаковывает поверх приложения, сохраняя локальные настройки
  → записывает новый hash и перезапускается
```

`/update` публикует полный Windows-релиз с embedded Python. После выхода будки
его применяет одноразовый PowerShell-скрипт, поэтому обновление может заменить
заблокированные `python.exe`, DLL и PYD без постоянного launcher-сервиса.
Одинаковый updater работает и в киоске, и при `script_devstart.bat`: аргумент
`--dev` сохраняется при автоматическом перезапуске.

Файл `.update_in_progress.json` захватывается ещё до сетевой проверки, поэтому
второй запуск не начинает параллельное скачивание и не доходит до backend/EDSDK.
Пока экран обновления открыт, приложение проверяет ZIP и заранее распаковывает
релиз во временную папку. Затем одноразовый установщик ждёт полного выхода всех
процессов embedded Python, копирует уже готовые файлы с повторами при временной
блокировке Windows и только после полного успеха атомарно записывает
`.update_hash`. Поэтому без интерфейса проходит только короткий этап замены
заблокированных файлов, а не полная распаковка. Затем приложение открывается
само в том же режиме и выполняет обычную проверку `status.json`, которая
подтверждает установленный hash. Если установка не удалась, текущая версия
аварийно запускается один раз без немедленной повторной попытки; следующий
обычный запуск снова попробует обновиться. Этапы и ошибка установщика
записываются в `photobooth.log`.

`status.json` хранит метаданные единственного полного ZIP. Поле `active: "full"`
сохранено для совместимости с уже установленными версиями. Отдельного номера
версии нет: версия — полный SHA-256 ZIP.

Будке доступ к GitHub не нужен: GitHub использует только VPS при публикации,
а будка всегда получает обновление через Яндекс Диск.

## Печать и шаблоны

Одна сессия снимает `num_photos` кадров из `config_app.json`. Рабочая
конфигурация снимает четыре кадра, после чего пользователь выбирает:

- `grid` — четыре кадра на одном горизонтальном листе 4x6;
- `strips` — один вертикальный шаблон 2x6 дублируется, а готовый лист
  поворачивается в 4x6; после печати лист разрезается на две одинаковые полоски.

Готовый JPEG имеет точный high-quality raster RX1HS: `3688x2480` с меткой
`600x600 DPI`. Драйвер преобразует его в нативный режим принтера `300x600`.
Grid-фон хранится сразу как `3688x2480`, а фон одной полоски — как
`1240x3688`; приложение дублирует полоску без промежуточного масштабирования.
Файлы фона, координаты кадров и итоговый `print_size` находятся в
`templates/<template_pack>/config.json`. Если размер пользовательского фона
отличается, приложение подгонит его через `ImageOps.fit` и запишет warning в лог.
Поле `label` задаёт подпись варианта на экране. Новые элементы в `templates`
появляются в выборе автоматически — отдельных кнопок во frontend нет.

После получения всех кадров будка один раз показывает экран «Обрабатываем
фото…». Четыре оригинала уменьшаются один раз и только в памяти, после чего из
них собираются реальные экранные превью всех настроенных вариантов. Уменьшенные
фото ограничены `720 px` по длинной стороне: это больше чем вдвое превышает
крупнейший слот текущих превью, но позволяет JPEG-декодеру Canon сразу работать
примерно в масштабе 1/8 по каждой стороне. Готовые превью имеют размер
`720x484`, а уменьшенные фоны кешируются рядом с оригиналами как
`*_preview.jpg`; при каждой сессии
проверяются размер и время изменения исходника, поэтому новый или заменённый фон
пересоздаётся автоматически. Итоговые превью сессии временно лежат только в
`photos/<session>/previews`, удаляются сразу после выбора (и при ошибке/новом
запуске приложения), а полноразмерный макет собирается только для выбранного
шаблона. Ни кеши фонов, ни превью сессии не входят в печатную очередь, Яндекс
Диск, манифест или Telegram.

При `print_enabled=true` JPEG напрямую рисуется в Windows printer DC.
`printer_name` задаёт точное имя принтера; пустое значение использует принтер
по умолчанию пользователя `Photobooth`. Для стрипов можно указать
`printer_name_strips` — отдельную очередь того же DNP-драйвера, в которой включён
фирменный `2inch cut`. Если поле пустое, обе раскладки печатаются через основную
очередь, а две полоски нужно разрезать вручную.

Вторую очередь создаёт `_setup_strips_printer.bat`. Сначала нужно установить и
проверить основную очередь, затем запустить батник на Windows: он запросит права
администратора, прочитает `printer_name` и `printer_name_strips` из
`config_app.json` и подключит вторую очередь к тому же драйверу и физическому
порту. Повторный запуск безопасен: совпадающая очередь не пересоздаётся, а при
конфликте драйвера или порта скрипт остановится, ничего не удаляя.

После создания откроются свойства новой очереди. На вкладке **Advanced** нужно
открыть **Printing Defaults**, включить фирменный параметр DNP `2inch cut` и
нажать Apply/OK. Стандартный Windows `Add-Printer` не умеет задавать private
DEVMODE-параметры DNP автоматически; приложение оставляет этот параметр из
defaults очереди, но само задаёт размер бумаги, ориентацию, DPI и одну копию.

Стандартные настройки DNP задаются приложением: paper option `202` (4x6),
одна копия, цвет, ICM Pictures и `print_dpi=600`. Для RX1HS это high-quality
режим: драйвер сам преобразует 600x600 вход в нативные 300x600.

Эти значения сверены с установленным пакетом DNP Windows 10 v1.1.3.0:
`PC/(6x4)=202`, Portrait и raster `3688x2480` для режима 600x600.

В Windows Printing Preferences этого пользователя один раз нужно проверить
borderless/margin off, glossy или matte и, если нужна автоматическая резка
полосок, включить `2inch cut` на отдельной очереди `printer_name_strips`.
Драйвер и private DNP-настройки могут отличаться между администратором и
киоск-пользователем, поэтому тестовая печать из Проводника под администратором
не проверяет профиль `Photobooth`.

## Переподключение камеры

Если Canon отключается по USB, приложение немедленно прерывает текущую съёмку,
очищает незавершённое видео и команды камеры и показывает экран поиска.
Частичная сессия остаётся локально для диагностики, но не попадает в очередь
печати или Яндекс Диска. После подключения камера настраивается заново, и будка
сама возвращается на главный экран без тапа и перезапуска приложения. Уже
завершённые сессии в очереди Яндекс Диска при этом не затрагиваются.

EDSDK и COM инициализируются один раз на весь camera worker. При USB-обрыве
закрывается и переоткрывается только camera session/reference; глобального
`EdsTerminateSDK` между попытками нет. Поиск повторяется с паузами 2, 4, 8 и
далее 10 секунд.

Для длительной автономной работы приложение при каждом открытии EDSDK-сессии
отключает Canon Auto power off и раз в 60 секунд продлевает shutdown timer.
Property events сразу сообщают об изменениях питания и температурных
ограничений, а раз в 10 минут в лог записываются также AE mode, доступные кадры
и свободное место. Новая сессия не запускается, если на диске фотографий меньше
`min_free_disk_gib` из `config_camera.json`. Пока `app.py` работает в Windows,
системный sleep и отключение дисплея также блокируются через process-scoped
execution-state request; после выхода приложения запрос снимается.

## Киоск-режим

`_setup_windows.bat` (от админа):
1. Создаёт/проверяет `python/` (через `_ensure_python.bat`)
2. Создаёт пользователя Photobooth с пустым бессрочным паролем
3. Shell = `python\pythonw.exe app.py` (вместо explorer.exe)
4. Автологин без пароля

Выход: Ctrl+Alt+Del → сменить пользователя.
Откат: `_undo_setup.bat`

## Облако

Основной transport — публичный REST API Яндекс Диска с OAuth-токеном.
Перед ивентом отдельная папка задаётся Telegram-командой `/event Название`.
После подтверждения команда атомарно обновляет `yadisk_folder` в конфигурациях
будки и VPS.
Оригиналы фото и видео доступны одновременно в двух представлениях:

```text
/
  /<event>/
    20260722_143205_<session>_photo_01.jpg
    ...
    20260722_143205_<session>_video.mp4
  /<event>_by_sessions/
    /2026-07-22_14-32-05_<session>/
      photo_01.jpg ... photo_04.jpg
      video.mp4
```

Коллекция `<event>_by_sessions` — сосед обычного event, а не его подпапка.
Поэтому гости, которым позже расшарят плоский `<event>`, не увидят дубликаты.
Сразу после получения четырёх кадров будка создаёт и публикует папку конкретной
сессии, пока параллельно идёт выбор шаблона и кодирование видео. Прямой
`public_url` Яндекс Диска подготавливается заранее; промежуточного
сайта/редиректа нет. Файлы появляются по этой стабильной ссылке по мере загрузки.

QR скрыт во время съёмки, обработки превью и выбора шаблона. Он может появиться
на следующем экране печати, как только готова публичная ссылка, и затем остаётся
на главном экране до начала следующей сессии. Пока медиа ещё передаются, подпись
просит гостя немного подождать и обновить страницу. `done_screen_seconds`
(сейчас 8 секунд) задаёт длительность отдельного экрана печати, а не срок жизни
QR.

Печатные `print_grid.jpg` и `print_strips.jpg` остаются только локальными файлами
для драйвера принтера. Они не входят в очередь, папку сессии, корень event или
манифест и не отправляются в Telegram.

Доставка сессии работает как durable outbox:

1. Будка заранее создаёт и публикует `<event>_by_sessions/<session>` для QR.
2. Четыре оригинала и видео сохраняются в локальную очередь `yadisk_queue.json`.
3. Все файлы загружаются в папку сессии и проверяются только
   по размеру/видимости ресурса. Полного локального чтения для MD5 больше нет.
4. Яндекс Диск серверно копирует файлы в плоский корень event. Дополнительной
   проверки size/MD5 копии нет; для ответа `202` ожидается только завершение
   операции копирования.
5. Последним загружается типизированное `session_ready` в стабильный
   `photobooth_system/control/to_vps`; оно содержит точный `event_folder`.
6. VPS скачивает плоские копии, проверяет их размер и отправляет в Telegram.
7. После успешной доставки VPS удаляет служебный JSON из `control/to_vps`;
   медиа не удаляются.

Приватная шина не зависит от активного event: будка раз в 10 секунд поллит
только `control/to_booth`, а VPS — только `control/to_vps`. В `to_vps` вместе
лежат `session_ready` и `command_response`, которые VPS разводит по независимым
asyncio workers. После успешной обработки служебные JSON удаляются, а результат
остаётся в логах и постоянных медиа.
Логи используют `control/logs`, обновления — `photobooth_system/updates`.

## Telegram-команды

- `/event Свадьба Ивановых 2026` — создать и активировать папку на будке и VPS;
- `/status` — state, камера, её health/последний disconnect, свободный диск,
  event, очередь и версия будки;
- `/run` — запустить фотосессию;
- `/logs`, `/clear_logs` — получить или очистить лог;
- `/get_config` — получить `photobooth_configs.txt` с текущими
  `config_app.json` и `config_camera.json`, а также отдельный `config_vps.json`
  напрямую с VPS, без перезапуска будки;
- `/restart` — подтверждённый перезапуск;
- `/update` — опубликовать полное обновление; установка после `/restart`;
- `/link` — опубликовать активную event-папку и вернуть публичную ссылку;
- `/<поле> <значение>` — изменить существующее рабочее поле
  `config_camera.json`, например `/iso 200`, `/iso auto`,
  `/white_balance auto` или `/continuous_af false`. Будка проверяет тип и
  `_..._options`, атомарно сохраняет значение и после подтверждения делает
  штатный рестарт. Во время фотосессии команда отклоняется.

Локальный лог состоит из активного `photobooth.log` и одного предыдущего
`photobooth.log.1`, по 200 KB каждый. `/logs` склеивает их в хронологическом
порядке и присылает одним файлом. `/clear_logs` полностью обнуляет активный лог,
удаляет все ротационные backup-файлы и продолжает запись с чистого состояния.
Поэтому следующий `/logs` содержит только события, произошедшие уже после
очистки (включая подтверждение самой команды `clear_logs`).

Смена event отклоняется, пока идёт сессия или локальная загрузка. Сессию команда
не прерывает; после освобождения будки команду нужно повторить.

## Смена аккаунта Диска

Никаких ID ресурсов или аккаунта в коде нет. Нужно заменить `YADISK_TOKEN` в
`.env` будки и VPS, перезапустить оба процесса, выполнить `/event ...`, затем
`/update`. Системные папки создаются автоматически; данные старого аккаунта не
копируются.
